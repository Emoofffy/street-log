# 文件編寫規格

> 本專案所有文件（`CLAUDE.md`、`docs/`、`README.md`、程式節標）照此寫。本文件自身即示範。
> 目標：沒參與過討論的第三方（或全新 context 的 agent），讀文件即能照著實作、並接續討論。
> 與 `~/Desktop/CODE/Trades/Charts/docs/DOC-STYLE.md` 同源；各專案自帶一份、獨立演進。

## 規則

1. **最少字表達完整意義**。能刪的字刪掉，刪不掉的留。
2. **原地即最終真相**。定案就改在原地，不靠附錄或後文推翻前文。
3. **術語先定義後使用**。頂部放名詞表，或首次出現即一句話定義。
4. **規範用正面陳述**。寫「該怎樣」，不堆「別怎樣」。
5. **狀態明確標記**。未定標 `待定`；已規劃未建標 `— 未建`。不留白讓人以為漏寫。
6. **不懸空引用**。引用的檔案／函式／節須存在；未寫的標「未撰寫」。
7. **冷讀者本位**。驗證手段：讓零背景讀者（或全新 context 的 agent）只讀文件，斷處即不足，沒提到的即可安全刪。
8. **寫在會存活的高度**。程式讀得到的（schema、簽名——本專案 schema 權威＝`app.js` 的 `seedDB()`）文件只給**指標**，不複製。該留的永遠是：目標、不變量、心智模型、承重詞彙——程式碼說不出口、且不隨實作變的。
9. **垂直三層 × 水平一主題一節：內容只准住一層，上層只指路**。垂直＝入口路由（`CLAUDE.md`：表格＋一句話＋指針，不放細節）→ 主題節（檔內 `====` 節）→ 程式本體（型別／schema 權威）。水平＝一主題一節、一節一標題、節首一行＝狀態＋一句職責；上層表格力求互斥且窮盡（每件事恰有一格）。增＝底層加一節＋上層加一行；刪＝反向兩筆；搬家＝改一個指針。**更新的單位是「重寫該節」**——不把更新塞進既有段落養成千字單行；段落長到不能一眼跳讀就拆節。
10. **狀態是狀態、不是日誌**。能力描述寫當下為真、改在原地，不追加「已補 X（日期）」。時間線的權威是 `git log`，任何 .md 不寫日期。

## 收尾流程（改完程式，資訊寫哪；一則資訊只寫一處、選最少被讀到的層）

1. **「何時改了什麼」** → `git commit` 訊息。時間線只此一處。
2. **「這節負責什麼」** → 該節節首職責行。
3. **「能力變了」** → `CLAUDE.md` 節地圖那行，改在原地（新增功能補一詞／改行為改描述／刪功能拿掉該句）。
4. **「踩了什麼坑／為何這樣設計／以後可再優化」** → 該節節首註解；累積成清單再開 `docs/UPGRADES.md`（現未建）。
5. **「程式與文件都說不清、下次卻關鍵的隱形前提」** → memory 檔（少數才寫）。

**刪東西**：grep 檔名／函式名／節名，清掉所有文件裡的死引用（規則 6）。

## 規則的學名（查外部資料用這些關鍵字）

| 本規格的做法 | 外界的名字 |
|---|---|
| 一處一寫、其他地方全用指標（規則 8、9） | Single Source of Truth ＋ DRY；防的病叫 documentation drift |
| 一主題一節、更新＝重寫該節（規則 9） | Topic-based authoring（代表實作：DITA） |
| 入口只給表格＋一句話，細節點進去才展開（規則 9） | Progressive disclosure |
| 「冷讀順序」與「主題挖掘表」雙入口 | Diátaxis（tutorial／how-to／reference／explanation 分軌不混寫） |
| 程式為權威、文件住程式旁、git 記時間線（規則 8、10） | Docs-as-code ＋ colocation；Living Documentation |
| 節首一行＝狀態＋一句話（規則 9） | 倒金字塔／BLUF（Bottom Line Up Front） |
| 上層表格互斥且窮盡（規則 9） | Minto Pyramid Principle ＋ MECE |
| 原子節、可定址、靠連結不靠層級（規則 9） | Zettelkasten |

## 反例（真實踩過的陷阱）

❌ 更新塞進既有段落，養成千字單行。
✅ 重寫該節；段落長到不能一眼跳讀就拆節。

❌ 能力地圖追加「已補匯出功能（7月）」。
✅ 改那行能力描述；何時補的看 `git log`。

❌ 引用 `docs/UPGRADES.md` 但檔案不存在、也沒標記。
✅ 引未建檔案一律標「現未建」／「未撰寫」。
